# Security readiness and private client signing

Status: approved by the owner on 16 November 2026 for implementation and deployment after testing. Agreement retention remains configurable and unset initially. No real client signatures are authorised by deployment.

## Intent and selected approaches

Make the existing Maple dashboard suitable for confidential client work without buying a separate document platform. First close verified security and recovery gaps; then allow a named client representative to review and sign a frozen confidentiality agreement through a private link. Existing project deliverable approvals remain team-recorded; signing a contract does not approve project delivery or an invoice.

The user selected built-in email-verified signing and company Google Drive for recurring encrypted off-server backups. Keep the current Next.js, Express, MongoDB and VPS architecture. Keep real company identities, agreements, recipients, recovery material and provider configuration outside this public repository.

Approaches considered:

1. Built-in email verification, explicit consent, immutable document and audit evidence — selected by the user for low cost and integration with existing drafts. This records agreement and mailbox control; it is not a certified digital-signature service or identity/KYC verification.
2. Licensed eSign provider integration — not selected for this version. It would require provider onboarding, fees and provider-specific identity and signature processing. The CCA describes this separate service at https://cca.gov.in/eSign.html.
3. Existing manual signing/upload — retained as an external option but does not satisfy the requested private signing flow.

For backups, the user chose a private company Google Drive destination. An S3-compatible bucket and Mac-only copies were alternatives; neither is the selected recurring destination. The Drive connection must be explicitly authorised with the intended company account; an unrelated connected personal Drive must not be used.

Builder-proposed defaults to be approved with this document: daily backups at the existing 07:45 IST time; maximum 30 calendar days of backup retention; seven-day private links; email verification codes valid for ten minutes; signing sessions valid for fifteen minutes. No paid subscription or enterprise plan is introduced. Existing email and Drive quotas still apply.

## Current evidence and scope

Production release b59e619 runs the web app on port 3006, API on 4006 and authenticated MongoDB on loopback port 27017. Nginx forwards the public domain to 127.0.0.1:3006. Web and API currently listen on all interfaces. The existing daily backup script writes unencrypted gzip archives, including environment files, without automatic retention or recurring off-server copy. The latest existing archive restored successfully into an isolated temporary database. Permissions are restrictive but do not provide encryption. The first scheduled daily run has not yet occurred at the time of this design.

Individual accounts, bcrypt password hashing, revocable sessions and server-side roles exist. Dashboard MFA does not. Live web responses lacked several security headers. The inspected Mac has FileVault off; other devices and staff confidentiality records were not verified. A configured Resend transport and document revision snapshots exist, but configuration alone is not evidence that the intended verification email will be delivered.

This is two coordinated releases: security/recovery first, client signing second. Builder review identified three boundaries that are made explicit below: consistent snapshot downtime, separate link/signature lifecycles, and the owner-selected retention policy for executed agreements. The technical work cannot certify every employee device, legal execution requirement, provider contract or staff obligation.

## Release one — server and account security

Bind production web and API listeners to loopback, preserving the existing proxy and health endpoints. Keep development host configuration explicit. Do not change other applications on the shared VPS. Add HSTS for the production HTTPS site without automatically preloading or covering every subdomain. Add MIME sniffing protection, a restrictive referrer policy, suitable permissions policy and framing protection. Use a CSP compatible with the existing site and document-preview iframe; prefer nonces on sensitive dynamic routes, avoid weakening the whole site merely to support a preview, and test public pages and admin previews. Signing pages must not load external tracking, third-party fonts, external images or analytics.

Review proxy trust and forwarded client IP handling against the actual Nginx → Next → Express chain. Rate limiting must not rely solely on an arbitrary client-supplied forwarded header. Redact passwords, OTPs, MFA secrets, recovery codes, session cookies and signing tokens from application logs. Use fragments rather than URL query/path secrets for private links, and never expose credentials in errors. Pin accepted JWT algorithms and keep current active-account/token-version revocation checks.

Add authenticator-app TOTP MFA for all dashboard users, with encrypted TOTP secrets and hashed, single-use recovery codes. Use a maintained implementation and standard test vectors. Bind and expire login challenges; require password verification before the second factor, limit attempts, reject replay of an accepted time-step, and issue no full-access token before successful MFA. Rate-limit password/challenge/enrolment/recovery paths. Never log the secret or recovery codes. Password-only sessions must not bypass an account's enrolled MFA through refresh or alternate login routes.

Roll out through an explicit enrolment mode. Accounts without MFA receive only a restricted enrolment session and cannot access client data, payroll or company settings once enforcement is enabled. Provide a controlled cutover period before enforcement, with the owner enrolled and a tested recovery path before migration; invalidate pre-enforcement sessions. Do not enforce while the only owner lacks a usable second factor and recovery method. MFA changes require recent password plus second-factor verification when already enrolled. Enrolment requires proof of a valid code and explicit acknowledgement that recovery codes have been saved. Users perform their own credential setup; the agent does not register itself as their authenticator. An owner cannot silently disable another person's MFA from an ordinary admin session; use a documented, audited operator recovery procedure with identity checks if all factors are lost.

Move deployment/bootstrap credential artifacts out of ordinary workspace/export locations after their necessary contents are secured and replacement recovery is verified. Keep runtime credentials in dedicated, permission-restricted server secret configuration; no secrets enter Git. Do not blindly rotate unrelated shared-provider keys. Inventory exposed historical setup copies and rotate applicable credentials in a controlled cutover where old plaintext copies could remain accessible. Environment-file encryption in backups is distinct from runtime secret access.

## Release one — encrypted backup and recovery

Use maintained command-line tooling (age for archive encryption and rclone for Drive transfer) obtained from official distribution channels, with version/integrity checks. A small checked-in orchestration script may coordinate them. The server receives only the backup encryption public recipient. Keep the private recovery identity off the VPS, in owner-controlled protected storage; a recoverable second copy and owner custody must be confirmed before replacing the old backup workflow or removing plaintext copies. Recovery secrets must never be printed in tool logs or stored in the repository. The exact recovery storage is established during setup, preferably the owner's password manager; macOS Keychain can protect the local working recovery secret. A recovery identity stored only on the unencrypted Mac filesystem is insufficient.

Authorise rclone for the intended company Google Drive with the smallest workable scope, preferably files it creates. Create a new private backup folder and scope the job to its verified folder ID. Do not share it publicly or place plaintext secrets, database dumps or recovery keys there. Store the Drive refresh credential in restricted server configuration and exclude that credential and backup recovery material from normal backup payloads.

For a consistent snapshot on the current standalone MongoDB, the proposed first version briefly drains/stops only Maple’s web/API writers and API scheduler at the scheduled backup time, captures the database and mutable files, and restarts the apps immediately before the off-server upload. This temporarily interrupts the site/dashboard, including new bookings and enquiries; failures must return an error rather than a false success. Enforce a short bounded maintenance window, automatic restart on every failure path, and a shared deploy/backup lock. Measure and report actual downtime in the supervised cutover. This maintenance tradeoff requires owner approval; converting the database to a replica set for an online backup strategy is the alternative, with a separate migration and recovery plan. Do not silently use an inconsistent live dump.

Each job must:

- acquire a non-overlap lock;
- stream a consistent MongoDB logical dump and the required CMS/media/application configuration into authenticated encrypted archives, without leaving an intermediate plaintext archive on disk;
- produce a manifest with archive names, creation time, sizes, hashes, source revision, encryption recipient identifier and schema/tool versions, with no client names or secrets;
- upload the encrypted archives and manifest to the private Drive folder, verify remote objects and record an off-server completion status only after verified upload;
- retain complete generation boundaries, detect partial failures, and never report success from file creation alone;
- maintain a hard maximum thirty-day retention ceiling for newly managed local and Drive backup generations, with targeted expiry limited to this folder and known manifests. Google Drive Trash must not silently add another retention period; implement permanent expiry only for verified job-owned expired backup objects and disclose this in setup;
- record success, failures, last off-server verification and available disk space. Show stale/failure state in an owner-only dashboard view. Send operational failure notices to the owner's agreed incident mailbox through the configured mail transport, with no backup contents or credentials. Alert on insufficient storage and failed expiry, not just failed dumps.

Before retiring the existing job, perform a fresh encrypted backup, upload it, retrieve it from Drive, decrypt using the off-server recovery identity, and restore MongoDB and required files into an isolated environment. Compare document/index and file hashes against a stable snapshot, not a concurrently changing live database. Do not restore over production. Exercise loss/unavailability of Drive, truncated archives, encryption failure, disk-full handling and missed runs. Keep the known-good existing backups until the new off-server restore and key custody are verified; then encrypt or safely retire the specifically inventoried legacy plaintext copies. Historical retained copies and restore-test directories count toward deletion commitments and must be addressed explicitly.

A monthly owner-assisted recovery drill verifies decryption with the off-server key; the server cannot autonomously decrypt if it holds only the public recipient. Routine daily checks verify archive/upload integrity, not full recovery. Document the distinction. Production content and secrets remain only in private encrypted evidence, not test fixtures.

## Release one — readiness and publication

Add an owner-only security/readiness view with separate observed technical state and dated owner attestations. Automatically show MFA enrolment/enforcement, backup/upload age, retention configuration and last restore evidence where the application can establish them. Treat a missing or failed probe as unknown/failing, not a pass. A server-generated status file exposed to the API must be permission-restricted and contain only safe summary fields; the client must not provide its own technical pass result.

Owner attestations cover authorised team devices with encryption and maintained protection, signed staff/contractor confidentiality terms, immediate offboarding ownership, supported cloud-account MFA, provider permissions and incident handling. Preserve who confirmed what and when. Scope these confirmations to people and systems actually granted client access; do not claim all eight employees were inspected. The user must complete FileVault activation and recovery-key custody on this Mac, and confirm or restrict other devices; opening the settings is assistance, not evidence encryption is active.

Publish the approved standard NDA only after its factual baseline is met and required attestations are recorded. Do not make external lawyer approval an invented software permission gate, and do not label publication as legal certification. Publication enables drafting; each project still needs complete fees, data-handling terms and authorised signers before issuing a signing link. Replace the draft-warning text only as part of this controlled publication. The clause choices already approved remain: mutual obligations; 100% of affected project fees with stated exceptions; the agreed incident contact; limited provider use; no unapproved training; 15-working-day active-data deletion; and 30-day maximum agreed backup retention once actually implemented. Do not overwrite company banking or billing details.

## Release two — private signing flow

Owner and Admin may prepare a signing request from a completed confidentiality draft. Only Owner may approve/issue or revoke the live client link in the first release. Members have no agreement or signing-record access. Signing links do not grant any dashboard access.

A request snapshots the exact document revision, project/client/company details, named signer and email, fee/SOW reference and currency/amount, approved provider/AI list, the client incident address, the agreed backup retention, and any required personal/production-data schedule. Introduce structured required agreement fields so remaining underscores or free-text reminders cannot be mistaken for completion. Missing required fields, unresolved variables, unpublished templates or unmet readiness block issuing. For this version use the existing INR monetary conventions; other currencies require an explicit supported extension. A project without agreed fees cannot use the project-fee cap template.

The link contains a random high-entropy secret in its fragment and a non-secret public request ID in its path. Store only a hash of the link secret. Reveal a newly issued link only to the issuing owner; provide a clearly labelled Copy private link action. The owner shares it manually; creating it does not send the agreement automatically. Rotate/revoke access without exposing the old secret. No guessing of record IDs grants access. Links expire after seven days, with explicit bounded configuration up to thirty days. Revocation and expiry are checked server-side on every protected action.

The initial public screen contains only generic Maple branding and a verification prompt. Before revealing the document, send a code only to the fixed signer email already bound to the request; visitors cannot choose arbitrary recipients. Verification codes are cryptographically random, protected with a server-side secret/hash, expire after ten minutes, allow at most five attempts, have resend cooldowns and per-request/per-recipient/global abuse budgets. Persist relevant limits so restarting the API does not erase them. Fail closed if delivery is unconfigured or fails; do not fall back to a pretend sent code. Use a dedicated transactional template, not a marketing campaign or subscription opt-in. Do not log the code or include confidential agreement text in the verification email.

After verification, establish a short-lived Secure/HttpOnly signing session bound to the specific request and signer; clear the link secret from visible browser history when safe. Client pages and APIs return no-store/noindex/no-referrer responses. No third-party assets or analytics receive the private token or document. A forwarded link alone is insufficient to see or sign the agreement.

The verified signer sees the frozen complete agreement, types their full name and capacity, confirms authority to represent the client, and explicitly consents to using this electronic signing process and signing that displayed revision. The final button states the action plainly. A typed signature is sufficient for version one; drawing/uploading a signature image and collecting identity documents are excluded. Capture the exact consent text/version, signer name and capacity, verified email, document digest, server time and minimally necessary audit metadata including IP/user agent with a short privacy explanation. Do not call an email code KYC, a certified signature, a qualified timestamp, or independent proof of the person's legal authority.

The client signs first. The request becomes Awaiting Maple signature, never Completed yet. The Owner must explicitly countersign as the configured authorised Maple representative, with recent MFA confirmation; an agent cannot sign on their behalf and an Admin cannot impersonate the representative. Completion requires both signatures on the same frozen revision. Keep agreement states separate from access-link states. Agreement states are Draft / Awaiting client / Awaiting Maple / Completed / Closed without completion; a link independently is Active / Expired / Revoked. Link expiry or revocation removes client access and prevents a new client signature, but does not erase an accepted signature or prevent an authorised Maple countersignature of that same frozen agreement. An owner may explicitly close an incomplete request with a recorded reason; this prevents further signing while retaining existing evidence and is not presented as legal rescission of any acceptance. Completed records cannot be closed as a substitute for a separate legal amendment or cancellation. Display both status dimensions and useful dates.

Store both signature events, the frozen document and completion evidence atomically in a bounded MongoDB record using conditional state transitions. The standalone database cannot be assumed to support multi-document transactions. Reject simultaneous duplicate signing, replay, stale sessions, mismatched revisions and revoked links. Key audit events and state updates must not diverge on partial failure. Reading/view analytics are secondary and must not interfere with signing correctness.

Generate a branded server-side PDF containing the exact frozen agreement, both signature statements and audit summary. Store its immutable bytes and digest with the completed record, bounded below MongoDB's document limit. A completion state is not committed unless the signed PDF is successfully generated and stored. The digest covers the appropriate frozen document content and separately the final PDF bytes; do not claim a self-referential PDF hash. The client may download the completed PDF through verified access while the link/session is valid; staff may download through their existing roles. An owner may issue new view-only access to a completed document without reopening or changing its signatures. Signed records cannot be edited or regenerated into a silently different contract. Corrections require a new request and new signatures; retain the prior record.

Existing source drafts may continue to be revised, but changes do not affect an issued request. Clearly show that a request uses an earlier frozen revision. No automatic company signature, client invitation email, client migration or real signature is part of test/deployment.

## Data and privacy lifecycle

Backup retention is not the retention period for signed legal records. Keep signed agreements as business records under an explicit owner-selected retention policy; do not invent a universal statutory period or automatically erase them at thirty days. The owner must choose the retention duration/basis and legal-hold handling before production links can be issued. Build this as required policy configuration, not a hardcoded inferred legal period; snapshot the notice shown to each signer. Until that policy is supplied, signed-record automatic purging stays disabled and production issuing stays disabled. The implementation plan can proceed with a configurable period, but the operational setup cannot claim readiness without this input. Agreed policy must cover the signed PDF, signer identity and identifying audit metadata together, and expiry, legal holds and eventual deletion must be auditable. Do not silently treat immutable as permanent storage. Limit collected audit information and expose it only to entitled parties. Expire unused OTPs/challenges/sessions automatically. Operational log retention must be assessed against applicable requirements; do not delete incident evidence merely to meet a backup setting. Project deletion requests must include reapplication after restores and the expressly agreed finite backup exception.

## Validation and rollout

Use synthetic contacts and documents for tests. Stub the mail transport in automated tests; any real delivery smoke test is to an owner-approved company inbox, never an actual client. Test access denial across Owner/Admin/Member, signed snapshot immutability, missing fields/readiness, link entropy and lifecycle, mail failure, OTP attempt and resend limits under concurrency, expiry boundaries, CSRF, token leakage, duplicate requests, both-party consent and completed PDF bytes, MFA enrolment/login/recovery/refresh/revocation, CSP and existing previews.

Run the repository's required backend suite, lint/type checks and production builds. Review implementation and security changes before deployment. Deploy additively with fresh backups, a documented rollback and health checks. Preserve payroll, bookings, enquiries and outreach. Restrict rollback after MFA enforcement so an older password-only release cannot silently reopen access; disable access or use a migration-compatible rollback.

Operational sequence: verified off-server recovery and server hardening → owner MFA/recovery and controlled enforcement → team/device/process attestations → publish the standard NDA → enable issuing client links after signing-flow validation. The signing UI may deploy earlier with issuing disabled until readiness is complete. Report implemented, deployed, verified and awaiting-human items separately.
